# THE NPC PIPELINE — from a record to a person a player can fight

⛔ **ERIK, 2026-09-08:** *"document HOW to pipeline new NPCs (authored and game generated) through to full in
game capability."*

⚠️ **Everything between the markers below is COMPUTED**, by calling the same functions `app.js` calls, on both
populations. ⛑ **Nothing here is a description of the code — a description is what rots.**

⚑ **Two populations, one set of doors:**

- **AUTHORED** — a record in `content/packs/valley/npcs/*.json` and the five other files the roster reads.
- **GENERATED** — a record minted in play by `generate('npc', ctx)` when the GM introduces someone new.

## THE SEVEN DOORS

⛔ **A person is playable only after the LAST one.** Passing six of seven looks exactly like success — which is why each is named, and why the two populations are checked separately.

| # | door | authored person | generated person |
|---|---|---|---|
| 1 | **REGISTERED** — something points at the record | the pack manifest lists the file | `persistGenerated` writes `character.generated.npc[id]` |
| 2 | **LOADED** — it is in a map the engine reads | `CONTENT.npcs[id]`, via `loadContent` | `character.npcRegistry[id]`, via the `meet` op |
| 3 | **RESOLVED** — the fight path can FIND it | `duelFromTarget` → `npcs[id]` | `duelFromTarget` → `character.npcRegistry[id]` ⚠️ **checked FIRST, so a stub wins over content** |
| 4 | **STANDING** — a tier and a level | authored `tier`/`level` win outright | ⛑ derived: `role` → `tierFromRole` → `tierFloor` |
| 5 | **KIT** — a real craft to declare | authored `abilities[]`, else the domain draw | ⛔ **neither — see below** |
| 6 | **OPPONENT** — a body to fight | `personOpponentFor` returns attributes, health, soak | same function, same shape |
| 7 | **HARM** — a verb that can threaten | a harm verb in the kit, or `notAnOpponent: true` | the bare strike only |

## THE GENERATED PATH, DRIVEN END-TO-END

⚠️ **A minted person is REQUIRED to carry `schemaVersion`, `id`, `name`, `role`, `spectrum`, `fears`** — and **none of the three inputs a kit is built from**.

| the record | tier | level | fightable | craft rows | menu rows |
|---|---|---|---|---|---|
| as `generate('npc')` leaves it | notable | **5** | ✅ yes | ⛔ **0** | 1 |
| a role that signals RANK (`Marshal of the Watch`) | heroic | **25** | ✅ yes | ⛔ **0** | 1 |
| + `domains` (what the merge would copy, if it had any) | heroic | **25** | ✅ yes | **28** | 28 |

⛔ **DOOR 5 IS THE HOLE, AND IT IS THE ONLY ONE.** Standing derives correctly — a role naming a rank lifts a minted person from **5** to **25** — and the body is real. ⚠️ **But the kit is empty at every level**, so a generated Marshal fights with a plain strike and a large health pool.

⚑ **THE MISSING INPUTS ARE `abilities`, `domains`, `tradition`.** The generation schema asks for none of them, `enforceFloors` adds none, and `reconcileGeneratedNpcWithMeet` copies `domains` only `if (rec[k] != null)` — a condition that is never true for a minted record.

⬜ **The authored side proves the doors themselves work:** **79 of 137** reachable authored people field at least one real craft through the same two functions. ⚠️ **The authored CENSUS is `docs/ROSTER.md` and is not recomputed here** — one ladder, deliberately.

## HOW TO ADD A PERSON

### An AUTHORED person

1. **Write the record** into `content/packs/valley/npcs/<file>.json` — `id`, `name`, `role`, `spectrum`,
   `fears` at minimum; `tier` if they are anything above a townsfolk.
2. **Register the file** in the pack manifest, or the loader never sees it.
3. **Give them a kit** — either an authored `abilities[]`, or `domains` so the domain draw can field one.
   ⛔ **A record with neither is reachable and fights with a plain strike.**
4. **Or declare them out** with `notAnOpponent: true`, so their absence from the fight path reads as a
   decision rather than an oversight.
5. **Regenerate and check:** `node scripts/roster.mjs --write` then `node scripts/npc_pipeline.mjs --check`.

### A GENERATED person

⚠️ **Nothing is authored — the doors are crossed by DERIVATION, and the derivation is what to check.**

1. `generate('npc', ctx)` mints the record and `persistGenerated` stores it under
   `character.generated.npc[id]`.
2. The GM's `meet` op creates the `npcRegistry` stub, and `reconcileGeneratedNpcWithMeet` re-homes the
   generated record onto the met id so **two ids never survive**.
3. **The merge copies only** `domains`, `domainsSource`, `people`, `peopleSource`, `appearance`, `gender`,
   `role` — ⚑ **and `role` is what carries them through door 4.**
4. `duelFromTarget` resolves `character.npcRegistry[id]` **before** `CONTENT.npcs[id]`, so a stub of the same
   id shadows an authored person. That is intended — the person you met in play is the person you met.
